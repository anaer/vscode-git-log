# ADR-0041: 交互式变基编辑器

**状态：** 提议中
**创建时间：** 2026-11-09

> **当前状态 / 核心结论：** 提案尚未实施。在 webview 内提供 todo 列表编辑器（拖拽排序 + pick / reword / edit / squash / fixup / drop），通过 `GIT_SEQUENCE_EDITOR` 一次性写回，冲突沿用现有中断状态条。下一步：确认条目上限与 merge commit 策略后立项。

---

## 背景

扩展已有 drop、squash、批量改信息等定点改写，但没有统一的 todo 视图；非相邻 squash、调整提交顺序、停下来修改某个中间提交都缺少入口，只能回命令行执行 `git rebase -i`。

## 决策

1. **入口**：提交右键「Interactive Rebase from Here…」，对 `<commit>^..HEAD` 生成 todo，最多 100 条。
2. **写回协议**：扩展生成一次性可执行的 Node 脚本并把它设为 `GIT_SEQUENCE_EDITOR`，脚本只把用户确认后的 todo 文本写入 `$1`；不依赖 shell，不修改仓库内文件，执行后立即清理。
3. **编辑器形态**：webview 内可拖拽排序的列表，每项选择 pick / reword / edit / squash / fixup / drop；非相邻 squash 通过「把目标移到一起再 squash」实现，不另设入口；reword 复用现有消息编辑对话框。
4. **中断处理**：复用现有中断状态条；`edit` 停下的提交在 continue 前允许打开文件修改，Continue / Abort 随时可用。
5. **边界与不做**：仅当前分支；允许脏工作区（`--autostash`，Git 版本不足则要求干净）；存在其它进行中的 Git 操作时拒绝；不支持 `--root` 与 `--onto` 跨分支变基。

## 后果

- **收益：** 把最常用的历史整理动作收进统一界面，非相邻 squash 与顺序调整不再需要命令行。
- **代价 / 权衡：** 这是当前风险最高的写操作，确认信息必须包含将被重写的提交数与是否已推送；实现与测试成本显著高于其余条目。
- **降级方向：** 保守——todo 生成、脚本写回、rebase 启动三步任一失败都不留下半完成状态。
- **未解决风险：** `GIT_SEQUENCE_EDITOR` 在 Windows 下的路径与可执行性需实测；rebase 中断后窗口重开时需重新读取 todo 状态。

## 实施位置

- 变基执行与 todo 生成：`src/git/GitOperationService.ts#GitOperationService`。
- 操作请求契约：`src/protocol/messages.ts#GitOperationRequest`。
- 编辑对话框：`webview/src/Dialogs.tsx#Dialogs`。
- 提交右键入口：`webview/src/ContextMenu.tsx#ContextMenu`。

## 下一步

确认条目上限、merge commit 是否默认保留（`--rebase-merges`），确认后单独立项实施。
