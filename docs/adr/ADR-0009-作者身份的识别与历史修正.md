# ADR-0009: 作者身份的识别与历史修正

**状态：** 提议中
**创建时间：** 2026-09-17

> **当前状态 / 核心结论：** 提议中，尚未实现。决定分两层处理作者身份：只读层解析 `.mailmap` 并在贡献者列表中合并身份别名（零风险，先行落地），破坏层把 `author` / `committer` 行纳入既有历史重写闭环（复用备份分支与 CAS）。下一步：先落只读层。

## 背景

User 过滤器为自由文本输入，靠 `--author=<正则>` 匹配（`src/git/logQuery.ts:46-48`），用户须自行回忆作者姓名或邮箱，全仓无 `shortlog` / `mailmap` 调用。另一方面，批量改写消息的闭环（拓扑重建 + 备份分支 + CAS `update-ref`）已具备，但只重写 commit message、**不触碰 `author` / `committer` 行**，因此错误的提交者信息在当前版本无法修正。

## 决策

1. **贡献者列表**：以 `git shortlog -sne --all` 驱动选择器，展示姓名、邮箱与提交数；点击后写入现有 `authors` 过滤器，不新增过滤器类型与协议消息。
2. **`.mailmap` 只读层**：解析仓库 `.mailmap`（含 `mailmap.file` / `mailmap.blob` 配置指向的替代位置），在提交列表、提交详情与贡献者列表中合并显示身份别名。该层**不修改任何 Git 对象**，可独立于改写层先行落地。
3. **作者身份改写**：在既有重建闭环中新增 `rewriteAuthorIdentity`，按「旧身份 → 新身份」映射重写 commit 的 `author` 与 `committer` 行，复用同一备份分支约定与 CAS `update-ref` 原子切换。
4. 改写范围与既有消息重写保持一致：目标为当前检出分支 HEAD、选定 commit 须在该分支可达、支持任意多选（不要求连续）、按拓扑序重建。
5. `.mailmap` 语法须覆盖 `Proper Name <proper@email> <commit@email>` 形式（含注释行与仅邮箱映射），否则会出现错误合并。

**不做什么：** 不引入 `git filter-repo` 或任何 Python 运行时；不保留 GPG / mergetag 签名（沿用既有剥离策略）；`.mailmap` 层不做任何写操作；不实现跨分支批量改写。

## 后果

- **收益：** 作者身份修正在只读层零风险可用；破坏层复用已建成的安全闭环，边际实现成本显著低于新建工具。
- **代价 / 权衡：** 改写 `author` 会改变全部受影响 commit 的 oid，破坏性与消息改写同级，必须同样走破坏性确认。
- **未解决风险：** `.mailmap` 的姓名与邮箱映射可能一对多，合并显示需定义确定性优先级，否则同一作者在不同视图下显示不一致。

## 实施位置

- 贡献者枚举：`src/git/GitService.ts` 新增 shortlog 查询；前端 User 过滤弹层 `webview/src/Toolbars.tsx:335`。
- mailmap 解析：`src/git/` 新增解析器；消费点为提交列表与 `webview/src/DetailsPane.tsx`。
- 重写闭环：`src/git/GitOperationService.ts` 的 `planMessageRewrite` / `patchMessageRewrite`（既有消息重写实现处），新增身份重写分支。
- 操作契约：`src/protocol/messages.ts` 的 `GitOperationRequest` 联合（当前 `:161-189`），新增 `rewriteAuthorIdentity`。
