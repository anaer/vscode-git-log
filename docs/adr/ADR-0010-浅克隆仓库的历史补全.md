# ADR-0010: 浅克隆仓库的历史补全

**状态：** 已接受
**创建时间：** 2026-09-17

> **当前状态 / 核心结论：** 已实现。仓库摘要新增 `isShallow`，浅克隆在提交区显示「历史被截断」提示，提示栏置于提交列表下方以避开列头。提示栏提供增量加深（主按钮 `--deepen=100`，下拉可选 500 / 1000，菜单向下展开并钳制在视口内）与整体补全（`git fetch --unshallow`）两条路径：前者只加深历史、不改 refspec，后者对 `--single-branch` 窄 refspec 把 `remote.<name>.fetch` 扩展为通配（在确认对话框逐字列出后再写）。历史重写前的浅克隆拒绝语义保留为兜底。下一步：无需后续动作。

## 背景

历史重写前会探测浅克隆并直接抛错「A complete clone is required; this repository is shallow.」（`src/git/GitOperationService.ts#assertCommitPatchStillCurrent`），界面既无感知也无恢复路径。同时普通 `fetch` 走 `--all --prune`（`src/git/GitOperationService.ts#buildOperationArguments` 的 `fetch` 分支），而单分支浅克隆的 `remote.<name>.fetch` 只覆盖一个分支，Fetch 拉不到其他分支——这正是「`--depth=1` 后取不到其他分支」的成因。此外 `--unshallow` 只有全有或全无两种结果，在大仓库上一次性下载完整历史代价过高，需要一条可分批推进的中间路径。

## 决策

1. 浅克隆探测落到仓库摘要采集：`inspectRepository` 在既有 `rev-parse` 批调用里加 `--is-shallow-repository`，`RepositorySummary` 增加 `isShallow`，使界面可感知该状态。
2. 提交区在 `isShallow` 为真且非裸仓库时显示「历史被截断」提示，避免用户把截断历史误认为完整历史。提示栏置于提交列表**下方**：此前放在顶部，因提交区是固定行数的 Grid（工具栏 / 列头 / 列表），提示栏挤入后会占掉一行并把列头压出可视区。
3. 新增 `fetchFullHistory` 动作，按是否带 `depth` 分两种语义：不带 `depth` 执行 `git fetch --unshallow <remote>`；带 `depth` 执行 `git fetch --deepen=<depth> <remote>`。远程按 `branch.<name>.remote` → `remote.pushDefault` → 唯一远程解析，多远程且无前两者时不猜测、直接拒绝。访问远程、体积可能很大，须先确认。
4. 对窄 refspec，**整体补全**动作把 `remote.<name>.fetch` 扩展为通配 `+refs/heads/*:refs/remotes/<remote>/*`；该配置变更在确认对话框中逐字列出后再执行，不静默写入。窄 refspec 判定：已配置 fetch refspec 且其左端不含 `*`（不覆盖全部分支）。
5. 补全完成后经既有刷新链路重取仓库摘要清除提示；refspec 扩展与后续 fetch 是尽力而为——`--unshallow` 成功后其失败只 `console.warn`，不误报整体操作失败（历史已恢复）。原「历史重写要求完整克隆」的拒绝语义保留为兜底。
6. 增量加深与整体补全是**两条独立路径**，共用一个动作入口。`--deepen` 的语义是「在当前深度上再增加 N 条」，因而可反复点击、逐步推进；深度一旦越过根提交，git 会自动清除 shallow 边界（无需再调 `--unshallow`，此时调它反而报 `--unshallow on a complete repository does not make sense`）。
7. 增量加深**不改动 refspec**：`--deepen` 只关乎历史深度，refspec 只关乎分支可见性，二者正交。若增量路径也扩展 refspec，会让「只想多看些历史」的操作顺带改变分支可见性，超出用户预期。
8. 加深下拉菜单**向下展开并双向钳制视口**：提示栏位于提交区底部，触发器贴近窗口下缘，若按「底部对齐、向上生长」定位，菜单在矮窗口下会被顶出上边界。定位控件与既有的 `webview/src/App.tsx#Workbench` 筛选弹层一致——先记录触发器锚点，再在 `useLayoutEffect` 中用实测高度求 `top`，并同时钳制 `top`/`right`，另挂 `resize` 与 `ResizeObserver` 以便窗口变化时重算。测量未就绪时以估算高度兜底。

**不做什么：** 不静默改写 `remote.<name>.fetch`；不在裸仓库上提供该动作；不自动触发 `--unshallow`；不在重写守卫里去掉浅克隆兜底；不让增量路径改动 refspec；不把加深菜单做成向上展开或脱离视口钳制。

## 后果

- **收益：** 「历史重写不可用」的死胡同错误变为可执行的恢复动作；顺带修复浅克隆下其他分支不可见的问题；大仓库可分批加深，不必一次性承担完整历史的下载成本。
- **代价 / 权衡：** `--unshallow` 下载完整历史，大仓库耗时与体积显著，因此必须显式确认；界面不无脑展示该动作（仅浅克隆可见）。增量加深按「再拉 N 条」而非「设为 N 条」计，可见条数会累加（当前 500 条时点「+1000」得 1500 条），需要在按钮文案与确认对话框中说清。主按钮取最小档（100）而非最大档：单次点击应是低代价的试探性操作，想一次拉更多再走下拉，从而把「代价大小」的决定权显式交回用户。
- **不做什么（残留）：** 若远程不可达，动作失败仍走既有 `classifyGitError`；未对「已浅但用户想保持浅」提供偏好开关；步长常量尚未做成用户可配置项。

## 验证

已实测（真实浅克隆夹具，`init` + `fetch --depth 1` 构造，本地 `git clone --depth` 会被 git 本地优化绕过故不采用）：

- 摘要采集：浅克隆 `inspectRepository` 得 `isShallow: true`，完整仓库该字段缺省。
- 恢复动作：单分支浅窄克隆经 `fetchFullHistory` 后 `rev-parse --is-shallow-repository` 转 `false`、`rev-list --count HEAD` 由 1 增至全部、`remote.origin.fetch` 变通配、`refs/remotes/origin/other` 出现。
- 增量加深：对 301 提交的仓库，从深度 1 连续 `--deepen 100` 得可见提交 1 → 101 → 201 → 301，验证 `--deepen` 确为累积语义；越界那次使 `--is-shallow-repository` 转 `false` 且 `.git/shallow` 消失，验证深度越过根提交会自动转完整。
- 守卫：缺确认时拒绝、无远程时拒绝、`buildOperationArguments` 在未解析远程时抛错、确认文案含 `refspecFrom`/`refspecTo` 逐字串；增量路径越界或非正整数深度抛 `Invalid fetch depth`。
- 协议：仅 `kind` 可过校验；`-x` 远程、含换行或超长的 refspec 一律拒绝；`depth` 仅接受正的安全整数且在 `MAX_FETCH_DEPTH` 之内。
- 前端：浅克隆显示提示条；主按钮 post `{kind:'fetchFullHistory',depth:1000}`，下拉项 post 所选档位，整体补全项 post 不带 `depth` 的同一动作，选择后菜单关闭；完整克隆不显示。
- 下拉定位：单元测试环境（jsdom）下 `getBoundingClientRect()` 恒返回零尺寸、`window.innerHeight` 为固定值，**无法**覆盖定位几何，故该项仅以人工核对为准；机制上采用与既有筛选弹层相同的「实测高度 + 双向钳制 + `resize` / `ResizeObserver` 重算」，并以估算高度兜底首帧。

测试：浅克隆相关用例覆盖在 `test/unit/repositoryDiscovery.test.ts`、`test/unit/protocol.test.ts`、`test/unit/GitOperationService.test.ts`、`test/unit/WorkbenchApp.test.tsx` 四处。提示条与下拉的用例以 `role="note"`、`role="menu"` 与 `aria-label` 定位，不依赖 DOM 位置，故提示栏改置列表下方、下拉改为向下展开后均无需调整。`npm run typecheck`、`npm run lint` 与 `npm run build` 均无报错。
