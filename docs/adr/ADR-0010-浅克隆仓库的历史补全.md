# ADR-0010: 浅克隆仓库的历史补全

**状态：** 提议中
**创建时间：** 2026-09-17

> **当前状态 / 核心结论：** 提议中，尚未实现。决定把浅克隆仓库从「历史重写前直接拒绝」改为「界面明示历史截断 + 提供 `git fetch --unshallow` 恢复动作」，并一并修复单分支浅克隆下 Fetch 拉不到其他分支的问题。下一步：待批准后实现。

## 背景

历史重写前会探测浅克隆并**直接抛错**「A complete clone is required; this repository is shallow.」（`src/git/GitOperationService.ts:872-873`），不提供任何恢复路径。同时 `fetch` 走 `--all --prune`（`src/git/GitOperationService.ts:123-126`），而单分支浅克隆的 `remote.<name>.fetch` 只覆盖一个分支，Fetch 无法拉到其他分支——这正是「`--depth=1` 后取不到其他分支」这一常见困扰的成因。

## 决策

1. 把浅克隆探测从「重写前的临时检查」上移到仓库摘要采集，`RepositorySummary` 增加 `isShallow` 字段，使界面可感知该状态。
2. 提交图顶部在 `isShallow` 为真时显示「历史被截断」提示，避免用户把截断历史误认为完整历史。
3. 新增 `fetchFullHistory` 动作，执行 `git fetch --unshallow`；该动作会访问远程，须先确认，并说明预计下载量可能很大。
4. 对单分支浅克隆，补全动作需同时把 `remote.<name>.fetch` 扩展为 `+refs/heads/*:refs/remotes/origin/*`；该配置变更必须在确认对话框中**逐字列出**后再执行，不得静默写入。
5. 补全完成后刷新仓库摘要并清除截断提示；原有「历史重写要求完整克隆」的拒绝语义保留为兜底。

**不做什么：** 不静默改写 `remote.<name>.fetch`；不在无远程或远程不可达的仓库上提供该动作；不自动触发 `--unshallow`。

## 后果

- **收益：** 把「历史重写不可用」的死胡同错误变为可执行的恢复动作；顺带修复浅克隆下其他分支不可见的问题。
- **代价 / 权衡：** `--unshallow` 会下载完整历史，大仓库的耗时与体积显著，因此必须由用户显式确认而非自动执行。
- **未解决风险：** 浅克隆的边界 commit 在补全后可能因 graft 边界重排而改变可达性，需在补全后重新校验一次仓库摘要而非沿用旧值。

## 实施位置

- 浅克隆探测：`src/git/GitOperationService.ts:857-873`（`rev-parse --is-shallow-repository`），上移至摘要采集。
- 摘要模型与采集：`src/shared/models.ts` 的 `RepositorySummary`；`src/repositories/discoverRepositories.ts`。
- 操作契约：`src/protocol/messages.ts` 的 `GitOperationRequest` 联合（当前 `:161-189`），新增 `fetchFullHistory`。
- 参数构造：`src/git/GitOperationService.ts` 的 `buildOperationArguments` `fetch` 分支（当前 `:123-126`）。
- 前端：`webview/src/CommitList.tsx` 顶部截断提示；`webview/src/Toolbars.tsx` 补全动作入口。

## 验证

待实现后补：① `git clone --depth 1` 的仓库显示截断提示且 `isShallow` 为真；② 补全后 `git rev-parse --is-shallow-repository` 返回 `false` 且完整历史可见；③ 单分支浅克隆补全后其他分支出现在 Refs 面板；④ 无远程仓库不出现该动作入口。
