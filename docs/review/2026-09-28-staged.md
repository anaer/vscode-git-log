## High

### `src/git/GitService.ts` — `readRemoteTags` / `reportRemoteTagFailure`：探测被取消时误报为远程故障，并永久毒化去重集合 [bug]

`readRemoteTags` 的 `.catch` 无条件调用 `reportRemoteTagFailure`。而 `GitRunner` 在 abort 时以
`GitCommandError(cancelled = true)` 拒绝（`src/git/GitRunner.ts:236`），取消并非故障。

取消是常规路径而非异常路径：`WorkbenchController#enrichRefsWithPushedTags` 在每次新加载时都会
`this.pushedTagsAbortController?.abort()`。

后果链条：

1. 用户刷新 / 切换仓库 → 上一次探测被取消 → catch 触发。
2. Output 面板写入 `[refs] remote origin <cancelled 详情>; its tags cannot be marked as pushed.` — 一条并不存在的故障。
3. `origin` 被写入 `reportedRemoteTagFailures`。
4. 此后**整个扩展宿主生命周期内**，`origin` 的任何真实故障（网络中断、认证过期、远端下线）都静默无输出。

即用户得到的是「刷新时噪音、真实故障时沉默」——诊断信号完全反了，且不可恢复。

仓库内已有相反约定，说明这是遗漏而非有意设计：`src/git/FileHistoryService.ts:217`、
`src/git/GitService.ts:1271`、`src/git/GitService.ts:1318` 均先排除 `!error.cancelled && !error.timedOut`
再作分支处理。

> **建议**：catch 内先过滤取消，再走上报。
> ```ts
> .catch((error: unknown) => {
>   if (error instanceof GitCommandError && error.cancelled) return undefined;
>   this.reportRemoteTagFailure(remote, error);
>   return undefined;
> })
> ```
> 补一条回归用例：先启动探测 → `abort()` → 断言 `diagnostics` 为空，且随后一次真实失败仍能上报。

### `src/git/GitService.ts` — `reportedRemoteTagFailures`：去重键只有 remote 名，跨仓库互相污染 [bug]

`GitService` 在 `src/extension.ts:318` 于 activate 时实例化一次，被全部仓库共享；
`getPushedTags(cwd, signal)` 按仓库传入 `cwd`，但去重集合是实例级字段且仅以 `remote` 名为键：

```ts
private readonly reportedRemoteTagFailures = new Set<string>();
```

后果：仓库 A 的 `origin` 失败后，仓库 B 的 `origin` 失败被静默吞掉。消息文案自称
`Reported once per remote per session.`，与实际作用域（全局 remote 名）不符——文案承诺的行为和代码行为不一致，
排障时会误导。

> **建议**：键改为仓库作用域，例如 `this.reportedRemoteTagFailures.add(`${cwd}\0${remote}`)`。
> 补一条跨仓库用例：仓库 A 失败 → 仓库 B 同名 remote 失败 → 断言两条诊断都在。

## Low

### `src/git/parsers/parseRefs.ts` — `withPushedTags` 对 tag 数量是 O(n²) [performance]

每个 tag ref 都对每个 remote 做一次线性 `tags.includes(ref.shortName)`。单 remote、N 个 tag 的仓库，
extension 侧代价为 N² 次字符串比较。典型仓库（N < 1000）无感；tag 数量过千的仓库（大型 monorepo、
长期打 tag 的发行线）会明显卡住富化步骤。

> **建议**：进入循环前先建一次反向索引 `Map<tagName, string[]>`，再单遍 map；测试可补一个 5000 tag 的规模用例。

### `src/protocol/messages.ts:242` — `pushedTagsLoaded.requestId` 无消费方 [maintainability]

全仓 grep 确认：`requestId` 只在 `WorkbenchController.ts:1178` 写入，
`webview/src/workbenchMessageProcessing.ts:221` 的 handler 从不读取它（其它消息用 `requestId` 维护
`race.requestById`）。属于新增协议里的死字段，未来读代码者会误以为存在按请求关联的逻辑。

> **建议**：二选一——删掉该字段，或在 handler 中用于诊断关联（例如 enrich 失败时按 requestId 上报）。

### `src/git/GitOperationService.ts:682` — `remotes[0] ?? ''` 是取不到的兜底分支 [maintainability]

第 681 行已保证 `remotes.length === 1`，故 `remotes[0]` 不可能为 `undefined`。
一旦走到 `''`，用户看到的是 `Invalid push remote: ` 这种内部校验文案，而不是
`This repository has no remote to push the tag to.` 这类可操作提示。

> **建议**：改为显式收窄（`const only = remotes[0]; if (only) return { remote: only };`），
> 与 `resolvePushPlan` 保持同一写法。

### `src/git/GitOperationService.ts:1077` — 新操作的用户文案为 `pushTag completed.` [style]

通用成功消息用 `${operation.kind} completed.`，`pushTag` 是新增 kind，用户会在界面上直接看到 camelCase。

> **建议**：为 `pushTag` 补一条可读文案（如 `Pushed tag v1.0.0 to origin.`）。模板本身是既有代码，
> 但新增 kind 让这条既有缺陷第一次进入用户视野。
